# 4.07 ID/Pass 찾기 기능 추가

> 파일명 안내: Windows 파일시스템은 `/`를 경로 구분자로 취급해 파일명에 쓸 수 없어 `ID·Pass`로 표기했습니다.

## 개요

로그인 페이지에 "아이디/비밀번호 찾기" 기능이 없는 상태다. 본 문서는 기능 설계와 구현 체크리스트를 정리한다. 이번 세션에서는 문서만 작성하며, 실제 코드 구현은 별도 세션에서 진행한다.

## 2. 설계 결정 사항 (사용자 확인 완료)

가입 시 이메일 외 별도 식별 정보(휴대폰 등)를 수집하지 않는 현재 스키마 기준으로, 두 가지 방향을 확인했다.

1. **아이디 찾기는 별도 기능으로 만들지 않는다.** 이메일이 곧 로그인 아이디이므로, 로그인 페이지에 "가입 시 사용한 이메일이 아이디입니다" 안내만 노출하고 "비밀번호 찾기" 링크로 유도한다.
2. **비밀번호 재설정 본인확인은 이메일 인증 코드(6자리)** 방식으로 한다. 기존 Resend 발송 인프라를 그대로 재사용하며, 별도 SMS 서비스 연동이 필요 없다.

이 결정에 따라 본 문서의 실제 구현 범위는 **"비밀번호 재설정" 기능 하나**로 좁혀진다.

## 3. 기능 정의

### 3.1 아이디 찾기 → 안내 문구로 대체

- 로그인 폼 상단 또는 "비밀번호를 잊으셨나요?" 링크 옆에 안내 텍스트 추가.
  - 예시 문구: "아이디는 가입 시 등록한 이메일 주소입니다."
- 별도 페이지/API 없음. 순수 UI 카피 변경.

### 3.2 비밀번호 재설정 (핵심 기능)

3단계 플로우로 설계한다.

```
[1단계: 이메일 입력]
      │  이메일 형식 검증 → 서버 액션 호출
      ▼
[서버] 계정 존재 + 비밀번호 로그인 가능 여부 확인
      │  (존재 여부와 무관하게 응답 메시지는 항상 동일 — 이메일 열거 공격 방지)
      │  가입된 계정이면 6자리 코드 생성 → 해시 저장 → Resend로 발송
      ▼
[2단계: 인증 코드 입력]
      │  코드 일치 + 만료시간(10분) 이내 + 시도 횟수 이내 확인
      ▼
[3단계: 새 비밀번호 설정]
      │  Zod로 비밀번호 규칙 검증 (registerSchema와 동일 규칙 재사용)
      ▼
[완료] hashedPassword 갱신 → 재설정 토큰 소비 처리 → 로그인 페이지로 이동
```

**Kakao 전용 계정(`hashedPassword === null`) 처리**: 재설정 요청 화면에서는 이메일 존재 여부를 노출하지 않아야 하므로, 이 경우도 1단계 응답은 동일하게 "이메일을 확인해 주세요"로 반환한다. 실제로는 코드 이메일 대신 "이 계정은 카카오 로그인으로 가입되어 있습니다. 카카오 로그인을 이용해 주세요" 안내 메일을 발송한다. 응답 자체로는 계정 존재를 구분할 수 없고, 메일함은 본인만 확인 가능하므로 안전하다.

## 4. 데이터 모델 설계

기존 `VerificationToken`은 `token String @unique`로 **컬럼 전체에 대한 전역 유니크 제약**이 걸려 있다. 6자리 코드(경우의 수 100만)를 이 테이블에 그대로 저장하면 사용자 간 충돌 가능성이 실질적으로 존재하고, 향후 이메일 인증 링크 기능과 용도가 섞일 위험도 있다. 재사용보다 **전용 테이블을 새로 추가하는 편이 더 단순하고 안전**하다고 판단했다.

```prisma
model PasswordResetToken {
  id         String    @id @default(cuid())
  userId     String
  codeHash   String    // 6자리 코드를 그대로 저장하지 않고 해시 저장
  expiresAt  DateTime
  attempts   Int       @default(0)
  consumedAt DateTime?
  createdAt  DateTime  @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@map("password_reset_tokens")
}
```

`User` 모델에 역방향 관계 1줄 추가.

```prisma
model User {
  // ...기존 필드 유지...
  passwordResetTokens PasswordResetToken[]
}
```

- 코드 재발급 시 기존 미사용 토큰은 무효화(삭제 또는 `consumedAt` 처리)하여 사용자당 활성 코드 1개만 유지한다.
- `codeHash`는 bcrypt 또는 sha256 중 택1 (기존 코드베이스가 비밀번호에 bcryptjs를 쓰고 있으므로 통일성 있게 bcryptjs 사용을 권장).

## 5. 서버 로직 설계 (Server Actions)

`src/app/actions/auth.ts`에 함수 3개를 추가하거나, 파일이 길어지면 `src/app/actions/password-reset.ts`로 분리한다 (기존 파일 66줄 수준이라 추가해도 800줄 기준에는 여유 있음. 관심사 분리 관점에서는 별도 파일 권장).

| 함수 | 입력 | 동작 | 응답 |
| --- | --- | --- | --- |
| `requestPasswordReset` | `email` | Rate Limit 확인 → 계정 조회 → 코드 생성/해시/저장 → 이메일 발송 | 존재 여부와 무관하게 동일한 성공 메시지 |
| `verifyResetCode` | `email`, `code` | 최신 토큰 조회 → 만료/시도횟수/일치 여부 확인 | 성공 시 3단계 진입 허용, 실패 시 `attempts` 증가 |
| `resetPassword` | `email`, `code`, `newPassword`, `confirmPassword` | 코드 재검증 → bcrypt 해시 → `User.hashedPassword` 갱신 → 토큰 `consumedAt` 처리 | 성공/실패 메시지 |

설계 메모.

- 기존 `registerUser`(`src/app/actions/auth.ts`)와 동일하게 `AuthResult` 타입(`{ success, message, fieldErrors? }`)을 재사용해 일관성을 유지한다.
- `verifyResetCode`와 `resetPassword`를 굳이 분리할지, 3단계 폼에서 코드+새 비밀번호를 한 번에 제출해 `resetPassword` 하나로 합칠지는 구현 단계에서 UX와 함께 결정한다. 단계별 즉시 피드백(코드가 틀렸을 때 바로 알려주기)을 원하면 분리, 단순함을 우선하면 통합이 낫다.
- 코드/이메일 값은 `console.log`로 남기지 않는다 (보안 규칙).

## 6. Zod 검증 스키마 (`src/lib/validations/auth.ts`에 추가)

```ts
export const requestResetSchema = z.object({
  email: z.string().email('올바른 이메일 형식이 아닙니다'),
})

export const verifyResetCodeSchema = z.object({
  email: z.string().email(),
  code: z.string().length(6, '인증 코드는 6자리입니다'),
})

export const resetPasswordSchema = z
  .object({
    email: z.string().email(),
    code: z.string().length(6),
    newPassword: z.string().min(8, '비밀번호는 8자 이상이어야 합니다'),
    confirmPassword: z.string(),
  })
  .refine((data) => data.newPassword === data.confirmPassword, {
    message: '비밀번호가 일치하지 않습니다',
    path: ['confirmPassword'],
  })
```

`registerSchema`의 비밀번호 규칙(8자 이상)과 동일하게 맞춘다.

## 7. Rate Limit 설계 (`src/lib/rate-limit.ts`에 추가)

```ts
export const passwordResetRequestRateLimit = redis
  ? new Ratelimit({
      redis,
      limiter: Ratelimit.slidingWindow(3, '10 m'),
      prefix: 'pw-reset-request',
    })
  : null

export const passwordResetVerifyRateLimit = redis
  ? new Ratelimit({
      redis,
      limiter: Ratelimit.slidingWindow(5, '10 m'),
      prefix: 'pw-reset-verify',
    })
  : null
```

- `requestPasswordReset`은 이메일 기준으로 10분당 3회 제한 (스팸 발송 방지).
- `verifyResetCode`/`resetPassword`는 이메일 기준 10분당 5회 제한 + `PasswordResetToken.attempts` 컬럼으로 코드 자체의 무차별 대입도 이중 차단.
- IP 기준 제한은 Server Action 내부에서 `headers()`(`next/headers`)로 `x-forwarded-for`를 읽어 추가할 수 있으나, 1차 구현에서는 이메일 기준 제한만으로 충분하다고 판단. 남용이 관측되면 추가.

## 9. 이메일 발송 설계

`education.ts`/`newsletter.ts`와 동일하게 동적 import + `RESEND_API_KEY` 존재 여부 가드 패턴을 따른다.

```ts
const { Resend } = await import('resend')
const resend = new Resend(process.env.RESEND_API_KEY)

await resend.emails.send({
  from: '팍스크리스티코리아 <noreply@발송도메인>',
  to: email,
  subject: '[팍스크리스티코리아] 비밀번호 재설정 인증 코드',
  html: `인증 코드: <strong>${code}</strong> (10분간 유효)`,
})
```

- 발송 실패 시에도 사용자에게는 동일한 성공 메시지를 반환하되, 서버 로그에는 실패를 남긴다 (`education.ts`의 `console.error('[Education] Resend email failed')` 패턴).
- Kakao 전용 계정에는 코드 대신 안내 메일을 발송 (3.2절 참고).

## 10. 보안 체크리스트

- [ ] 계정 존재 여부와 무관하게 1단계 응답 메시지 동일화 (이메일 열거 공격 방지)
- [ ] 6자리 코드는 해시로 저장, 평문 저장 금지
- [ ] 코드 만료시간 10분, 만료 후 재검증 불가
- [ ] `attempts` 컬럼으로 코드 대입 시도 횟수 제한 (예: 5회 초과 시 해당 토큰 즉시 무효화)
- [ ] 코드 검증/재설정 성공 시 해당 토큰 `consumedAt` 처리 (재사용 불가)
- [ ] 재발급 시 이전 미사용 토큰 무효화 (사용자당 활성 토큰 1개)
- [ ] Rate Limit 적용 (요청/검증 각각)
- [ ] 코드·이메일 값 서버 로그에 남기지 않음
- [ ] 비밀번호 재설정 성공 후 안내 문구에 "다시 로그인해 주세요" 명시 (JWT 세션 특성상 기존 세션 강제 무효화는 어려움 — 11절 참고)

## 11. 알려진 한계 / 향후 고려사항

- **JWT 세션 즉시 무효화 불가**: `authConfig.session.strategy = 'jwt'`이므로 비밀번호를 재설정해도 이미 발급된 JWT는 만료 전까지 유효하다. 즉시 무효화가 필요하면 DB 세션 전략 전환 또는 별도 토큰 블랙리스트가 필요한데, 이는 이번 기능 범위를 넘어서므로 현재는 다루지 않는다.
- **아이디 찾기 요구가 실제로 있다면**: 향후 회원가입 시 휴대폰 번호를 필수 항목으로 추가하고 SMS 인증 서비스(NHN Cloud, Twilio 등)를 붙이는 방향으로 재검토한다. 현재는 범위 밖.
